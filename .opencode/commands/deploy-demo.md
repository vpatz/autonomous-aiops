---
description: Deploy the AIOps demo on the current OpenShift cluster and print its dashboard and MLflow URLs
---

Deploy the live demo from this repository root using the active `oc` context. Execute the deployment and verify it. Use sections 3–5 of `0_cluster_setup/README.md`, `3_langgraph_workflow/README.md`, and `5_load_generator/README.md` as the runbooks.

1. **Check the target.** Report `oc whoami --show-server` and `oc whoami`. Verify the `/prep-cluster` prerequisites, particularly `my-vm-project`, HCO Available, the `rhel10` DataSource Ready, the manifest storage classes (or the prepared cluster's equivalent classes), AAP and MLflow. If the platform is incomplete, identify the blocker and direct the operator to `/prep-cluster`. Use `my-vm-project` for the workloads and `aap` for automation.
2. **Provision the four guests and Linux MCP.** Inspect existing named VMs, DataVolumes, credentials and deployments first. On a new installation use a demo SSH key outside Git and create the matching `linux-mcp-ssh` Secret. Render a private copy of `1_vm_services/vm-deploy.yaml` outside the checkout, replace **all** example authorized keys with the matching public key, disable guest password login or use a privately supplied password, and set `LINUX_MCP_BASE_URL` using this cluster's ingress domain. Apply the prepared manifest. Preserve existing VM disks, keys and cloud-init on reruns; start stopped demo VMs and restore `linux-mcp` to one replica if needed. Wait for the four VMs to become Ready and `linux-mcp` to roll out. Never put private keys, passwords, tokens or event-stream URLs into Git or chat.
3. **Wire integrations.** Apply `playbooks/vm-recovery-rbac.yaml`. For real recovery, use the active cluster's AAP gateway and the runbook to create or reuse and sync both AAP projects, the four-host inventory, scoped credentials, three recovery templates, event stream and rulebook activation. Verify the activation is running and the launcher can execute the templates. Set `eda-config` from the full HTTPS POST URL and credentials of **this** stream. Reuse `llm-config` or create it from operator-provided private settings. If optional inputs or AAP access are unavailable, continue deploying the core demo and explicitly report heuristic detection or mock execution rather than claiming those integrations work.
4. **Deploy the workflow and generator.** Run `python3 3_langgraph_workflow/build_pod_manifest.py --check`, `oc apply -f 3_langgraph_workflow/workflow-pod.yaml`, and `oc apply -k 5_load_generator`. If embedded code or startup Secret values changed, recreate only the `aiops-workflow` Pod using the manifest. Ensure the generator has one replica. The legacy stage-2 collector is not part of this deployment; the chaos injector is an on-demand workstation CLI.
5. **Verify and print links.** Use bounded waits (`oc wait` and `oc rollout status`) and report any failed condition with its cause. Check that `/api/dashboard` returns all four expected VM names with `vm.status=flowing`, the generator logs show real HTTP responses, and MLflow is Available. Use these lookups to print a labeled list of clickable URLs in the final response:
   - **AIOps dashboard:** `oc -n my-vm-project get route aiops-workflow -o jsonpath='{.spec.host}'` (prefix the returned host with `https://`).
   - **MLflow:** `oc get consolelink mlflow -o jsonpath='{.spec.href}'` (use the full returned URL). Point to workspace `my-vm-project`, experiment `aiops-workflow`, then **Traces**.

Report readiness separately from the URLs: an authentication redirect can be expected, but an unavailable route or missing console link is not a successful check. End with the deployed component status and any remaining operator input. Do not inject faults as a deployment test.
