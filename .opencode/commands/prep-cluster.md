---
description: Install and verify the OpenShift platform prerequisites for the AIOps demo
---

Prepare the OpenShift cluster selected by the current `oc` context for this repository's demo. Execute the setup and verify readiness. Use sections 1 and 2 of `0_cluster_setup/README.md` and the manifests in that directory as the runbook. `cluster-state.json` is a reference inventory, not an install manifest.

1. **Identify the target.** Run `oc whoami`, `oc whoami --show-server`, `oc get clusterversion version`, and `oc get nodes`. Report the server being prepared. If not logged in, ask the operator to log in with `oc` in their terminal and resume; do not request a token in chat. Check permissions to create namespaces, OLM resources, and cluster-scoped custom resources.
2. **Check storage and compute.** Verify a schedulable virtualization-capable node, a default filesystem storage class, snapshot/clone-capable RWO block storage for the VM disks, RWO filesystem storage for MLflow and RWX storage for AAP Hub. Match the classes in `0_cluster_setup/aap.yaml`, `0_cluster_setup/mlflow.yaml`, and `1_vm_services/vm-deploy.yaml`. If using equivalent classes, use temporary copies of the prerequisite manifests and report the VM storage-class override needed later. If storage is not provisioned, identify the missing CSI/provider setup from section 1. An ODF Subscription alone cannot connect an external Ceph cluster; do not invent provider configuration or credentials.
3. **Install the operators.** Ensure `my-vm-project` and the install namespaces exist. Use `oc` to create any missing OLM `Subscription` and, where required, `OperatorGroup` resources for the **four packages** in the section 2 table. Use the documented namespace, catalog and channel, with `sourceNamespace: openshift-marketplace`. Check the package's supported install modes for OperatorGroup scope; reuse the global group in `openshift-operators`. Inspect existing subscriptions/groups first, reuse compatible installations and report conflicts instead of replacing them. Wait for each Subscription's current CSV to reach `Succeeded` before applying its custom resources.
4. **Deploy the instances and wait for them**, following the runbook's bounded `oc wait` commands:
   - Apply `0_cluster_setup/hyperconverged.yaml`. Verify HCO `Available` and the `rhel10` DataSource `Ready` in `openshift-virtualization-os-images`.
   - Apply `0_cluster_setup/aap.yaml`. Verify AAP `Successful` in `aap`, its component pods, and the gateway route.
   - Check cert-manager readiness. Create `default-dsci` from `0_cluster_setup/dscinitialization.yaml` if absent and wait for `Ready`; reuse an existing initialization targeting `opendatahub`.
   - Apply `0_cluster_setup/datasciencecluster.yaml` on a new cluster. If a DSC exists, enable only `dashboard.standard` and `mlflowoperator` on that instance, preserving other components. Wait for `MLflowOperatorReady`, then apply `0_cluster_setup/mlflow.yaml` and verify MLflow `Available`, its PVC `Bound`, and its Deployment ready.
5. **Report the result.** List each prerequisite as ready or blocked, with the observed condition, the cluster's actual AAP and MLflow URLs, and any operator input still needed (for example AAP entitlement). On a failed wait, inspect the relevant conditions and namespace events and give the next concrete step. A successful `oc apply` alone is not readiness.

Finish at the platform boundary: leave the VMs, Linux MCP, workflow, load generator, chaos scenarios and AAP demo jobs for the application deployment steps in the runbook. Rerunning `/prep-cluster` on an already prepared cluster should verify and reuse healthy resources without restarting them.
